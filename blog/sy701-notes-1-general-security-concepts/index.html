SY701 Notes - 1. General Security Concepts

2026-08-19Notes

Information Security vs Information Systems Security

-
Information security: protecting the data itself (records, files, anything stored or transmitted) from being seen, changed, or destroyed by the wrong party.
-
Information systems security: protecting the platforms that hold and move that data (servers, endpoints, network gear).
-
Practical examples: locking down customer records, restricting sensitive folders, watching logs for anomalies.

CIA Triad

PillarGoalTypical controls
ConfidentialityOnly the right people can read the dataencryption, access control, data masking
IntegrityData stays accurate and unaltered unless an authorized change happenshashing, checksums, digital signatures
AvailabilitySystems and data stay reachable when neededredundancy, backups, failover, DR planning

Non-Repudiation

-
Guarantees someone can't later deny they took an action or sent something.
-
Digital signatures are the usual mechanism: sign a document, and the signature ties the identity to that exact content, proving both who signed and that nothing changed afterward.

AAA (Authentication, Authorization, Accounting)

-
Identification: the claim of who someone is, usually just a username.
-
Authentication: proving identity (password + MFA at login).
-
Authorization: deciding what that identity is allowed to touch (only assigned folders are reachable).
-
Accounting: the trail left behind (login time, data sent/received, logout time; used for audits and investigations).

Authenticating Systems and Devices

-
Devices often can't type a password and shouldn't have one stored on them anyway.
-
Fix: issue a digitally signed certificate to the device instead of a credential.
-
Organization runs its own CA, signs a certificate for the device, other systems (VPN gateways, management software) trust that CA and validate the device off the cert.

Authorization Models

-
Direct user-to-resource mapping doesn't scale: managing individual grants per user against every resource gets unmanageable and opaque.
-
Fix: insert an authorization model (roles, groups, attributes) between users/services and the data/applications they need.
-
Benefit: fewer relationships to track, administration simplifies, model supports any number of users or resources without redesign.

Security Control Categories

-
Technical: enforced through technology (firewalls, encryption, MFA).
-
Managerial: governance-level, paperwork and process (risk assessments, policy, audits).
-
Operational: the day-to-day human processes that keep security running (awareness training, incident response, change management).
-
Physical: controls over the physical space (locks, cameras, badges, guards).

Security Control Types (by function)

-
Preventive: blocks the event before it happens (firewall rule, door lock, following policy, guard shack checking ID).
-
Detective: notices the event after/while it's happening, doesn't necessarily stop access (system logs, login report review, property patrols, motion detectors).
-
Corrective: applies after detection to reverse or limit damage (restoring from backup after ransomware, incident reporting policy, calling law enforcement, fire extinguisher).
-
Deterrent: discourages an attempt without directly blocking it (application splash screen, threat of demotion, staffed reception desk, posted warning signs).
-
Compensating: substitutes for a control that isn't available or sufficient, often temporary (firewall blocking a specific app instead of patching it, separation of duties, requiring simultaneous guard duty, backup generator after outage).
-
Directive: points a subject toward compliance through instruction rather than enforcement, comparatively weak on its own (store sensitive files in a protected folder, compliance policy, security awareness training, "Authorized Personnel Only" sign).
-
Categories and types overlap: same control can land in more than one category, organizations mix and match, lists aren't exhaustive.

Threats, Vulnerabilities, Risk

-
Threat: any actor or event capable of causing harm.
-
Vulnerability: a weakness that could be exploited.
-
Risk: the combination, the chance a threat actually exploits a vulnerability and causes damage.
-
Chain example: attacker (threat) + unpatched server (vulnerability) = possible server compromise (risk).

Gap Analysis

-
Method of comparing where things stand now against where they should be, to surface what's missing.
-
Example: current state has no MFA on admin accounts, desired state requires it everywhere; the gap is exactly that missing MFA coverage.
-
Can be a large effort: weeks or months, broad participant list, heavy on data gathering and technical research.
-
Baseline picked from a framework: internal goal set, or a formal standard like NIST SP 800-171 (protecting controlled unclassified info) or ISO/IEC 27001 (information security management systems).
-
People/process evaluation: baseline current staff experience and training, review existing IT systems and policies against the chosen framework.
-
Output is a gap analysis report: current-state description, baseline objectives, and recommendations (time, money, change control) to close the gap. Often visualized as a requirements-by-location matrix (red/yellow/green per control area).

Zero Trust

-
Model built around never assuming trust by default, verifying every request regardless of source.
-
Core practices: confirm identity every time, apply least privilege, keep monitoring continuous, segment access into smaller zones, and operate as though a breach has already happened.
-
Motivation: traditional networks are open once inside the firewall perimeter; zero trust removes that implicit internal trust.

Planes of Operation

PlaneJobExamples
Data planeMoves and processes the actual trafficframe/packet forwarding, trunking, encrypting, NAT
Control planeGoverns how the data plane behavespolicy/rule definition, routing tables, session tables, NAT tables
-
Applies across physical, virtual, and cloud components alike.

Control Plane Components

-
Adaptive identity: trust decision weighs more than just credentials, source location, connection type, and IP all factor in.
-
Policy decision point (PDP): the umbrella process that reaches an authentication decision, made up of two pieces:
-
Threat scope reduction: shrink the number of possible entry points an attacker could use.
-
Policy-driven access control: adaptive identity signals combined with a predefined rule set.

Data Plane Component

-
Policy enforcement point (PEP): the gatekeeper sitting on the data plane between subject/system and the resource, allows, monitors, or terminates the connection. Can be built from multiple components working together.
-
Flow: subject/system reaches the PEP untrusted, PEP checks with the PDP (policy engine + administrator) on the control plane, traffic that clears moves to the enterprise resource as trusted.

Security Zones

-
Broad trust categorization rather than a strict one-to-one relationship: trusted vs untrusted, internal vs external network, specific VPNs, specific departments (marketing, IT, accounting, HR).
-
Zone alone can be enough to deny traffic (untrusted to trusted blocked outright).
-
Some zone-to-zone traffic is implicitly trusted (trusted to internal, for example).

Physical Security

-
Barricades and bollards: channel foot/vehicle traffic through a controlled point, can escalate to concrete barriers or moats for extreme cases; limited in what they prevent.
-
Access control vestibules: interlocking double-door entry, only one door can be unlocked at a time, forces controlled single-person (or single-group) passage.
-
Fencing: obvious perimeter marker, can be transparent or opaque, built sturdy enough to resist cutting, height/razor wire discourages climbing.
-
Video surveillance (CCTV): can substitute for physical guards, cameras networked and recorded over time, motion recognition triggers alerts, object detection can pick out a license plate or face.
-
Guards and badges: staffed reception validates identity of arrivals, two-person integrity/control requires simultaneous presence so no single person has unsupervised access to an asset, badges carry photo/name/details and log electronically, must stay worn at all times.
-
Lighting: more coverage generally deters attackers (harder to approach unseen), design has to account for angles/shadows/glare, matters for facial recognition on camera.
-
Sensors:
Sensor typeDetection method
InfraredInfrared radiation in light or dark, common in motion detectors
PressureChange in force, used in floor and window sensors
MicrowaveMovement across large areas
UltrasonicReflected ultrasonic sound waves, picks up motion/collisions

Deception and Disruption

-
Goal: lure attackers into a fake environment to study them and waste their effort, given the "attacker" poking around is often automated.
-
Honeypot: single decoy system built to attract and trap intrusion attempts; many open-source options exist; ongoing challenge to keep the fake convincing.
-
Honeynet: a fuller decoy network built from multiple honeypots (fake servers, workstations, routers, switches, firewalls), more sources of activity to observe.
-
Honeyfile: bait file dropped into shares with an enticing name (passwords.txt), alerts on access, functions as a virtual bear trap.
-
Honeytoken: traceable fake data seeded into the honeynet so a leak can be traced back to its source; examples include fake API credentials that alert on use, planted fake email addresses to see who contacts them, and fake database records, browser cookies, or web page pixels.

Data Classification

-
Labels applied to data based on how sensitive it is and how much protection it needs: public, internal, confidential, restricted.
-
Classification drives access rules, storage requirements, transmission rules, and disposal method.

Data Handling Practices

-
Keep sensitive data only in approved storage locations.
-
Encrypt files that hold sensitive content.
-
Gate access by role.
-
Never move confidential data through personal email.
-
Stick to sanctioned cloud services.
-
Follow whatever retention schedule applies.

Data Loss Prevention (DLP)

-
Technology that watches for, and can stop, unauthorized movement of data.
-
Monitors channels like email, endpoint copy/paste or USB activity, cloud uploads, web traffic, removable media.
-
Example: a DLP rule catches an outbound email containing credit card numbers and blocks it before it leaves the organization.

Retention and Disposal

-
Retention: how long data has to be kept before it can go.
-
Disposal: securely getting rid of data once it's past that point.
-
Disposal methods: shredding, wiping, degaussing, physical destruction, or a secure deletion workflow for cloud-hosted data.

Privacy Data Categories

-
PII (Personally Identifiable Information): name, address, phone number, anything that identifies a specific person.
-
SPII (Sensitive PII): higher-sensitivity identifiers like a Social Security number or financial account details.
-
PHI (Protected Health Information): medical records and related health data.

Cryptography Basics

-
Umbrella term for methods that transform information or prove its authenticity/integrity.
-
Supports all four pillars: confidentiality, integrity, authentication, non-repudiation.
-
Core terms: plaintext (readable original), ciphertext (unreadable transformed output), encryption (plaintext to ciphertext with a key), decryption (reverse, with the correct key).
-
Example use: encrypting a laptop's drive so a theft doesn't expose the data on it.

Symmetric vs Asymmetric Encryption

SymmetricAsymmetric
KeysOne shared key for encrypt and decryptKey pair: public + private
SpeedFast, good for bulk dataSlower

Example algorithmsAESRSA, ECC

Key Escrow

-
A third party (sometimes internal, sometimes external) holds a copy of decryption keys.
-
Legitimate use cases: business continuity if an employee is unreachable, government/legal access to partner data under court order.
-
Controversial by nature, still shows up as a business requirement; trust in the third party and the conditions controlling their access matter as much as the key itself.

Encrypting Data

-
Data at rest: protecting data sitting on storage (SSD, HDD, USB, cloud storage).
-
Database encryption: protects stored data and its transmission.
-
Transport encryption: protects data crossing the network. HTTPS handles it at the application layer; a VPN encrypts everything sent over the connection regardless of application (client-based VPN over SSL/TLS, site-to-site VPN over IPsec).
-
Algorithm choice: both sides must agree on the same algorithm before encrypting; tradeoffs are security level, speed, and implementation complexity, details usually hidden from the end user.
-
Key length: bigger keys resist brute force better since more combinations to try. Symmetric keys commonly 128-bit or larger; asymmetric keys need to be much larger for equivalent strength (3,072-bit or larger is common) because of the math relationship between the key pair.
-
Key stretching: strengthens a weak key by running it through repeated processing (hash the password, hash that hash, repeat), aka key strengthening. Forces a brute-force attacker to redo that entire chain per guess even though the underlying key is small.

Key Exchange

-
Core problem: sharing an encryption key across an insecure medium without physically handing it over.
-
Out-of-band exchange: key shared through a separate channel from the data (phone call, courier, in person).
-
In-band exchange: key shared over the same network, so it needs its own protection, typically wrapped in asymmetric encryption.
-
Common pattern: client generates a random symmetric key, encrypts it with the server's public key, server decrypts with its private key; that shared secret becomes the session key. Session keys should be ephemeral (changed often, unpredictable).
-
Symmetric key from asymmetric keys: each side combines its own private key with the other party's public key to independently derive the same symmetric key (Diffie-Hellman style), without ever transmitting the symmetric key itself.

Encryption Technologies

-
TPM (Trusted Platform Module): spec for cryptographic hardware built into a device. Includes a crypto processor (random number/key generation), persistent memory (unique keys burned in at manufacturing), and versatile memory (storage keys, config info, securely holds BitLocker keys). Password-protected against dictionary attacks.
-
HSM (Hardware Security Module): dedicated high-end cryptographic hardware for large environments, run in clusters with redundant power, stores large volumes of keys securely, offloads crypto processing (acceleration) from other devices, can serve as a key backup location.
-
Key management system: centralizes key handling across many services (on-prem or cloud), often third-party software, keeps encryption keys separate from the data they protect, associates keys with specific users/services, rotates on a schedule, logs key use.
-
Secure enclave: isolated, protected processing area for secrets, often a separate hardware processor with its own boot ROM, true random number generator, real-time memory encryption, root cryptographic keys, and hardware AES support; monitors the system boot process independently.

Hashing

-
Takes input of any size and produces a fixed-length output; one-way, can't be reversed back to the original.
-
Used to verify integrity rather than to hide content.
-
Common uses: checking a downloaded file hasn't been tampered with, storing password hashes instead of plaintext passwords, comparing forensic evidence without altering the original.
-
Algorithms referenced in the exam: SHA-256, MD5 (legacy, has a known collision problem since 1996, don't use for anything important).
-
Collision: two different inputs producing the same hash output; shouldn't happen with a well-designed algorithm, breaks the "unique fingerprint" guarantee when it does.
-
Salting: random data mixed into a password before hashing, unique per user, typically stored alongside the resulting hash. Same password produces a different hash per user, defeats precomputed rainbow-table lookups, and slows (without fully stopping) brute-force reversal.

Digital Signatures

-
Cryptographic proof covering authenticity, integrity, and non-repudiation together.
-
What a valid signature demonstrates: who signed the content, that the content hasn't been altered since signing, and that the signer can't plausibly claim they didn't sign it.

Obfuscation

-
Making something unclear without necessarily making it impossible to understand, given the right technique to reverse it.
-
Steganography: hiding a message inside an unrelated carrier ("covertext") so its presence isn't obvious. Variants: network-based (embedding messages in TCP packet fields), image-based (message hidden inside image data), invisible watermarks (e.g. yellow tracking dots printers embed), audio steganography (message interlaced into a digital audio file), video steganography (image steganography applied at scale across a frame sequence, managing signal-to-noise so the payload stays hidden).
-
Data masking: hides part of a value from view while leaving the underlying data intact in storage; access controls determine who sees the unmasked version. Techniques include substituting, shuffling, encrypting, or masking out characters.
-
Tokenization: swaps sensitive data for an unrelated placeholder token generated by a token service; original and token aren't mathematically related, so it's neither encryption nor hashing and carries no decryption overhead. Common in card payment flows: card registered once with a token service, the token (not the real card number) is what actually moves through the transaction.

Hashing and Digital Signatures (Recap)

-
Digital signature = hash of the message encrypted with the signer's private key, appended to the message.
-
Creation: hash the plaintext, encrypt that hash with the private key, ship plaintext + encrypted hash together.
-
Verification: recipient decrypts the signature with the signer's public key to recover the original hash, independently hashes the received plaintext, compares the two. Match confirms integrity (unaltered) and authentication (right sender); mismatch invalidates the signature.
-
Signing only needs the private key on the hash, not the whole message encrypted, so the message itself doesn't have to stay confidential to be signed.

Blockchain Technology

-
Distributed ledger: transaction record kept and replicated across every participant (node) rather than one central authority.
-
Flow: a transaction is requested, broadcast to every node in the decentralized network for verification, verified transaction gets bundled into a new block with other recent transactions, a hash is calculated from the prior blocks and added to the new block, the block is appended to the chain and pushed to all nodes.
-
Tamper resistance: altering any block changes its hash and every subsequent hash in the chain; the altered chain no longer matches what the rest of the network holds, so it gets rejected.
-
Practical uses: payment processing, digital identification, supply chain monitoring, digital voting.

Certificates and PKI

-
Certificate: a digital record that ties an identity to a public key.
-
PKI (Public Key Infrastructure): the whole system for issuing, managing, distributing, and revoking those certificates.
-
CA (Certificate Authority): the trusted party that actually issues certificates.
-
Where certificates show up: HTTPS, VPN authentication, encrypted email, device identity, code signing.

Certificate Details and Lifecycle

-
Format: X.509 standard. Fields include serial number, version, signature algorithm, issuer, subject (cert holder), public key, extensions.
-
Certificate signing request (CSR): applicant generates a key pair, sends the public key plus identifying info to a CA; CA validates the request (confirms DNS/email/website ownership), signs it with the CA's private key, returns the signed certificate.
-
Root of trust: everything in IT security traces back to some inherently trusted component (hardware, firmware, HSM, secure enclave, or the CA itself) that vouches for what follows.
-
Third-party CAs: built into browsers by default, purchased certs are trusted by anyone using that browser, CA vets the requester and may demand extra verification.
-
Private CAs: organization runs its own CA in-house, needed at medium-to-large scale, every internal device has to be configured to trust it (Windows Certificate Services, OpenCA).
-
Self-signed certificates: no public CA involved, fine when the organization is the only consumer, requires installing the CA's own cert/chain on trusting devices to behave like a purchased one.
-
Wildcard certificates: use the Subject Alternative Name (SAN) extension to cover multiple names under one domain (e.g. *.professormesser.com), avoids issuing a separate cert per subdomain.
-
Certificate Revocation List (CRL): CA-maintained list of revoked certs; can grow large, changes constantly. Example: CVE-2014-0160 (Heartbleed) exposed private keys on affected web servers, forcing mass reissue and revocation of the exposed certs.
-
OCSP (Online Certificate Status Protocol): browser/client checks revocation status directly with an OCSP responder over HTTP, lighter than pulling a full CRL, but support isn't universal across browsers/apps.
-
OCSP stapling: certificate holder checks its own status and "staples" a CA-signed status attestation into the TLS handshake, removing the need for every client to query the CA directly (better scalability than raw OCSP).

Key Management

-
Poor key handling undermines even strong encryption algorithms, so the key lifecycle matters as much as the algorithm choice.
-
Good habits: rotate keys periodically, restrict who can touch them, store them somewhere secure, revoke certificates once compromised, split key-management duties across people, and use an HSM or secure vault where it fits.

Asset Management

-
The discipline of tracking, protecting, maintaining, and eventually retiring everything the organization owns, hardware, software, data, cloud services, accounts, licenses, network gear, business processes included.
-
Underlying logic: security can't defend an asset nobody knows exists.

Asset Inventory

-
A record of assets and the details that matter for managing them.
-
Feeds into patching, vulnerability management, incident response, audits, and lifecycle decisions.
-
Typical fields tracked: name, asset ID, owner, department, location, IP address, hostname, OS, installed software, business function, criticality, data classification, patch status, warranty/support status.

Asset Classification

-
Labeling assets by importance, sensitivity, or business impact, which then dictates how tightly they get protected.
-
Categories mirror data classification: public, internal, confidential, restricted, critical.
-
Example: a public marketing site and a payroll database shouldn't get the same access controls, the payroll data is far more sensitive.

Asset Lifecycle

#

#

#

#

#

#

Change Management

-
Formal process for requesting, reviewing, approving, implementing, and documenting any modification to systems.
-
Purpose: cut down on downtime, misconfiguration, and changes nobody signed off on.
-
Covers things like patches, firewall rule edits, system upgrades, cloud config changes, access control changes.

Change Record Components

-
Description of the change
-
Business justification
-
Systems it touches
-
Risk/impact assessment
-
Approval
-
Implementation steps
-
Test plan
-
Backout plan (rollback path if it fails)
-
Scheduled maintenance window
-

Change Approval Process

-
Typical flow: submit request form, state the purpose, define scope, schedule date/time, identify affected systems and impact, run risk analysis, get sign-off from the change control board, collect end-user acceptance once complete.
-
Ownership: one individual or team owns the process (not necessarily the hands doing the work), keeps it followed and up to date. Example: shipping/receiving owns the label-printer upgrade process even though IT executes the change.
-
Stakeholders: anyone impacted by the change, not always obvious, can range from a single person to the whole company; they want input into the process.
-
Impact analysis: assign a risk value (high/medium/low); a "fix" can fail to fix anything, break something else, cause OS failures, or corrupt data. Skipping the change entirely carries its own risk: security vulnerability, application unavailability, unexpected downtime elsewhere.
-
Test results: run the change in a sandboxed environment first (isolated from production, no real-world connection), confirm before deploying; sandbox testing can't cover every possible outcome.
-
Backout plan: assume the change will go wrong and prepare to revert; some changes are hard to reverse, so backups have to be solid going in.
-
Maintenance window: often the hardest part to nail down; daytime changes risk hitting production load, overnight is usually safer but tough for 24/7 shops, seasonal blackout periods apply too (retail freezes changes during holidays).
-
Standard operating procedure: change management should be documented, published somewhere accessible (intranet), and treated as a living document updated as the process itself changes.

Technical Change Management

-
Change management decides what needs to change; the technical team handles how.
-
Allow list / deny list: security policy controls which applications can execute.
-
Restricted activities: change scope defines exactly which components are covered; approval isn't a blank check to touch anything, and scope may need expanding mid-window since not every outcome can be anticipated up front.
-
Downtime: services eventually go unavailable during a change, usually scheduled off-hours; can sometimes be avoided by switching to a secondary system, upgrading the primary, then switching back.
-
Restarts: applying a new config often needs a service restart, OS reboot, or switch power cycle; worth checking whether the system can recover cleanly from a hard power loss too. Restarting a service/daemon may take seconds to minutes; restarting an application means closing it fully and launching a new instance.
-
Legacy applications: predate the current team and may outlast it too; often unsupported by the original developer, which makes internal staff the de facto support team. Document the quirks and become the in-house expert rather than fearing the unknown.
-
Dependencies: completing one change may require completing another first (a service won't start without another active service, an app needs a specific library version). Dependencies can span systems (firewall code before firewall management software), which complicates sequencing.
-
Documentation: changes make docs stale fast, so updating diagrams, addressing schemes, and policies/procedures should be baked into the change process itself.
-
Version control: tracks changes to a file or config over time so a previous state can be restored easily; applies to router configs, OS patches, application registry entries. Not always native, some devices need extra management software to support it.
