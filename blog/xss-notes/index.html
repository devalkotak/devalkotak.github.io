What is XSS?

Cross-Site Scripting lets an attacker inject malicious code or client-side scripts into an application that then executes in the victim's own browser. The key distinction from SQL injection or command injection: XSS is a client-side vulnerability — you're not attacking the application server, you're attacking the application's users.

How it works (Example) — a banking app lets users pick English/French, passed as a lang parameter in the URL, which gets reflected back into the page's client-side code:

#
The attacker probes the app and discovers the lang parameter isn't restricted to en/fr — it accepts arbitrary strings
#
They host a malicious script on their own server (attacker-server.net) and construct a URL where lang calls that script
#
Clicking the link themselves would just execute the script in the attacker's own browser — pointless. To have any value, the attacker needs the victim (Alice) to click it — this variant is called reflected XSS, and it needs a phishing component to deliver it
#
Alice checks the link's domain before clicking (good security hygiene), sees it's genuinely her bank's domain, and clicks — reasonably, since the domain really is legitimate
#
The page loads normally and she does her banking as intended — but in the background, the injected script runs in her browser, reads her cookie store for that application, and exfiltrates her session token to the attacker

Why the attacker can't just host the exploit on their own server and skip all this: browsers enforce the Same-Origin Policy (SOP) — a script on attacker.com cannot read the responses or cookie data belonging to bank.com. The only way to get at bank.com's cookies is to get code to actually execute as bank.com — which is exactly what injecting into the vulnerable parameter achieves, since the malicious script is now running in the context of the legitimate domain, not the attacker's.

Types of XSS

Reflected XSS

The type in the example above — user input is reflected directly back in the immediate response to the request that submitted it. Requires a phishing/delivery component, since the payload only fires when the victim is tricked into visiting a crafted URL.

Stored XSS

Similar to reflected, except the malicious input gets stored by the application (in a database, typically) and served back to every user who later views that content — no phishing link needed, since the payload is already sitting on a page other users will visit organically. Meaningfully more dangerous for exactly that reason: reflected XSS compromises one victim per delivered link; stored XSS can compromise everyone who visits the affected page.

Real-world precedent: the 2005 MySpace "Samy" worm. An attacker named Samy planted a stored XSS payload on his own profile page. Anyone who viewed his profile had the script execute in their browser, which (1) added Samy as their friend and (2) copied the same malicious script onto their own profile page — so the next person to view that victim's profile got infected too, and the cycle repeated. It spread exponentially until MySpace had to take the site offline entirely to strip the payload from every infected profile — a textbook XSS worm.

DOM-Based XSS

Harder to find and exploit than the other two. Some background first: the DOM (Document Object Model) is the browser's in-memory representation of a page's HTML/XML — when a page loads, the browser parses the HTML into the DOM, and JavaScript on the page can read and dynamically modify that DOM at runtime.

DOM-based XSS happens when client-side JavaScript takes attacker-controllable input and passes it into a sink — a potentially dangerous function/property that can alter the page or execute code — without validating it first.

Contrast with reflected XSS, using the same idea from two different angles:

-
Reflected: the server inserts your input directly into the HTML response — e.g. a message GET parameter gets written straight into a <p> tag server-side. If unvalidated, injecting <script>alert(document.cookie)</script> works because the browser parses that injected markup as real HTML/JS when the page renders. The payload is visible if you view the page source.
-
DOM-based: the page itself never changes server-side — the HTML response looks identical either way. Instead, client-side JavaScript already on the page reads your input (e.g. from a search box) and writes it into a DOM property at runtime — e.g. element.innerHTML = searchValue. Because <script> tags inserted via innerHTML don't execute per the HTML5 spec, exploiting this sink specifically needs a different payload shape — e.g. an <img> tag with a deliberately broken src so its onerror handler fires your code instead. The takeaway: the vulnerability lives entirely in how the client-side script handles the input, not in what the server sends back, which is exactly why it's harder to spot from the outside.
What an Attacker Can Do With XSS

Once code execution is achieved in the victim's browser, the usual playbook:

-
Impersonate the victim — most commonly by stealing their session token, which only works if the token is stored somewhere JavaScript can reach: a cookie without HttpOnly set, or localStorage/sessionStorage
-
Perform any action the victim can perform, and read anything they can read — the script runs with the victim's own privileges in the application
-
Inject a trojan login form that mimics the real one, harvests credentials, and (for a more convincing attack) silently relays them to the real login endpoint too, so the victim logs in successfully and never suspects anything happened
-
Deface the application with inappropriate or politically motivated content
Impact of XSS Attacks

Depends entirely on the specific XSS type found and the attacker's actual goal:

-
Pure defacement: Integrity is heavily hit, Confidentiality and Availability largely untouched
-
Full account takeover: all three (Confidentiality, Integrity, Availability) can be affected
-
Attackers routinely chain XSS with other bugs or with functionality normally reserved for privileged users to escalate impact dramatically — a real example cited: a Magento vulnerability where a stored XSS bug was chained into arbitrary code execution.

How common/critical? XSS had its own dedicated OWASP Top 10 category in 2010, 2013, and 2017, but in the most recent list it was folded into the broader "Injection" category — currently the 3rd most critical risk facing web applications. In direct testing experience: essentially every application tested has had at least one XSS vulnerability somewhere — it remains extremely common despite the long history of known defenses.

How to Find and Exploit XSS Vulnerabilities

Methodology differs somewhat by type, so covered per type below.

Reflected XSS

#
Identify every endpoint where user-supplied data gets reflected back in the response — URL query parameters, the URL path itself, even HTTP headers in some cases.
#
Submit a unique, arbitrary marker string at each candidate location — something short, alphanumeric, with no tag characters or special syntax, unlikely to collide with existing content or get eaten by a filter (e.g. test12564).
#
Search responses for that marker. Finding it confirms the input is reflected somewhere — it does not by itself confirm XSS, but it means that location now needs to be tested specifically.
#
Determine the reflection context — the exact syntactic position the input lands in (inside a tag attribute value, inside a <script> block, inside a URL-bearing attribute like href, etc.). The right payload depends entirely on this context; there's no universal payload.
#
Build and test a context-specific payload (usually via Burp Repeater first), then always confirm in an actual browser before calling it vulnerable — a payload that looks reflected in a proxy response isn't proof it actually executes.

Worked payload examples by context:

Reflection contextPayload approach
Inside an attribute value, e.g. value="test12564""><script>alert(1)</script> — close the quote, close the tag, inject a new element. The resulting markup has a stray trailing "> from the original tag, but browsers render past minor syntax errors like this without breaking
Inside an attribute value, staying inside the tag" onfocus="alert(1) — cleaner (no dangling markup), but needs user interaction (a click/focus) to trigger, so it's the weaker of the two options
Inside an existing <script> block, e.g. var a = 'test12564';';alert(1);var foo=' — close the string with a single quote, terminate the statement, inject your code, then open a dummy variable (foo) to soak up the trailing quote from the original code so nothing errors out
Inside an href attributeEither the javascript: pseudo-protocol directly in the URL, or break out with # (an inert page-fragment marker) followed by an onclick handler

Resource: PortSwigger's XSS Cheat Sheet lists every usable tag and event handler combination, cross-referenced against which browsers support each — used constantly in practice rather than memorizing payloads from scratch.

Bypassing filters/defenses, depending on what's blocked:

-
Specific tags/event handlers blocked → brute-force the XSS cheat sheet's tag list to find what's still allowed, then brute-force event handlers for that tag
-
No quotes allowed at all → build strings via String.fromCharCode(...) instead of quoted literals
-
Specific keywords blocked (e.g. the literal string javascript) → break the keyword up with whitespace (including encoded whitespace like a tab character) — browsers are lenient about whitespace inside HTML/JS in ways naive filters often aren't
-
Full technique catalog: OWASP's XSS Filter Evasion Cheat Sheet

Stored XSS

Same discovery methodology as reflected — map every input vector, submit a unique marker string, look for it reflected. The real difference: stored XSS content can surface in a completely different location than where it was submitted, so confirming it takes reviewing all of the application's content and functionality broadly, not just re-checking the same response. Once you find where the marker resurfaces, the rest of the process (determine context → build payload → confirm in browser) is identical to reflected.

DOM-Based XSS

Genuinely harder, since the vulnerability lives in client-side logic rather than the server response.

#
Review every piece of client-side JavaScript for sinks — dangerous functions/properties that write attacker-influenced data into the DOM: document.write, document.writeln, document.domain, element.innerHTML, and similar.
#
Once a sink is found, inject the unique marker string and use browser dev tools to trace the actual execution path from source (where the input enters) to sink (where it gets used dangerously) — understanding that path is what tells you the exact shape the payload needs to take.
#
Build and test the payload against that specific sink (recall: <script> tags injected via innerHTML won't execute per spec — an <img onerror=...> or equivalent is often needed instead).
Automated Exploitation Tools
-
Web Application Vulnerability Scanners — any decent scanner should reliably catch most reflected XSS, since it's comparatively mechanical to detect. Stored and DOM-based XSS are harder for scanners — some catch them, some miss them — so manual verification alongside an automated scan is standard practice, not optional. Burp Suite Pro is the personal preference cited, though free/open-source options exist across a range of budgets.
How to Prevent XSS Vulnerabilities

Primary Defense — Output Encoding

Encode all user-controllable data at the point of output, before it's rendered — this ensures it's displayed as inert data, never interpreted as executable code. The correct encoding is context-dependent: HTML encoding for data inserted into HTML, JavaScript encoding for data inserted into a script context, and so on — a single encoding scheme doesn't cover every context an application might reflect input into. Never hand-roll an encoding routine (same rule as with crypto) — use a well-established library for your language/framework; OWASP maintains a list of recommended options per stack.

Primary Defense — Input Validation on Arrival

Only accept input matching what's actually expected for that field — e.g. an age field should accept integers only, nothing else. An allowlist is always more secure than a denylist, but a denylist is sometimes unavoidable in practice — which is exactly why input filtering is classified as a defense-in-depth layer rather than a complete standalone defense: a denylist is inherently incomplete against a sufficiently creative payload.

Defense in Depth — Response Headers

Content-Type and X-Content-Type-Options tell the browser what format a response actually is. Set correctly, they stop a browser from executing injected HTML/JS on a response that was never meant to be interpreted as such. Doesn't apply everywhere — many pages legitimately need to serve HTML/JS — so this is a supplementary layer, not the official defense.

Defense in Depth — Content Security Policy (CSP)

A browser-enforced mechanism restricting what resources a page is allowed to load and whether the page can be framed by others (relevant to both XSS and clickjacking). Configured via the Content-Security-Policy response header, containing one or more semicolon-separated directives. A strict example policy might allow images/scripts/AJAX/CSS only from the page's own origin and nothing else — under that policy, a script an attacker tries to load from their own server simply won't execute, since it isn't same-origin. CSP is powerful but genuinely deep enough to be its own topic; treat it as the last line of defense, not the first thing to reach for.

Summary: output encoding and input validation on arrival are the two things you should always be doing; response headers and CSP are valuable additional layers on top, not substitutes for the first two.
