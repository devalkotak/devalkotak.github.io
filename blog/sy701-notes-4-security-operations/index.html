Secure Baselines & Hardening Targets

-
A baseline is the documented, locked-down configuration state (firewall settings, patch level, OS file versions) every instance of an app/OS/device is expected to match.
-
Baselines usually come from the vendor: application developer, OS manufacturer, appliance manufacturer. Windows alone has 3,000+ group policy settings, only a subset security-relevant.
-
Deploy via a central console (Active Directory group policy, MDM) rather than by hand, automation is what makes it feasible across hundreds/thousands of devices.
-
Integrity checks confirm devices still match the baseline; drift needs immediate correction, not a ticket for later.
-
Maintenance: most settings are "set once, rarely touched" best practice, but some need revisiting when a new vuln surfaces, an app gets updated, or a new OS ships. Test changes first, conflicting baselines are common in complex environments.

Hardening by target type

TargetKey hardening points
Mobile devicesManufacturer hardening checklists, timely OS/app patching, segmentation (separate corporate vs. personal data), managed via MDM
WorkstationsConstant patch/update cycle (OS, apps, firmware), monthly patch automation, joined to a policy management system (AD group policy), strip out unneeded software
Network infra (switches, routers)Purpose-built devices with limited OS access, disable default credentials, apply vendor security updates (infrequent but important)
Cloud infrastructureLock down the cloud management workstation (holds the keys), least privilege on all services/settings/permissions, EDR on anything touching the cloud, backups including cloud-to-cloud (C2C)
ServersWide OS variety (Windows, Linux, iOS, Android), OS/service pack patching, password length/complexity + account lockout, restrict network access, AV/anti-malware

Embedded systemsHardware/software built for one specific function (or as part of a bigger system), hard to upgrade (some, like watches/TVs, easier than others), patch what can be patched, segment and firewall the rest
IoT devicesHeating/cooling, lighting, wearables, smart speakers; weak vendor defaults (change them), slow to get updates, put them on their own VLAN

Securing Wireless and Mobile

-
Site surveys: sample the existing wireless spectrum, map access points already in the area (not all controlled by the org), plan around interference, build a heat map of signal strength. Surveys need to repeat, RF environments change.
-
Wireless survey tools: signal coverage, interference detection, vendor built-in tools, third-party tools, spectrum analyzer.
-
MDM (Mobile Device Management): centralized management of company- and user-owned mobile devices, sets policy on apps/data/camera/etc., can control an entire device or just a work "partition," enforces screen lock/PIN.
-
Device ownership models:
ModelWho owns itNotes
BYOD (Bring Your Own Device)EmployeeHardest to secure, dual-purpose device, unclear data protection at sale/trade-in
COPE (Corporate Owned, Personally Enabled)CompanyCompany buys it, used for both work and personal, org keeps full control, wipeable anytime
CYOD (Choose Your Own Device)Company (user picks model)Same control model as COPE, just user choice of hardware
-
Cellular: "cell" phones split coverage into geographic cells on 4G/5G; security concerns are traffic monitoring, location tracking, worldwide reachability of the device.
-
Wi-Fi: same security concerns as any Wi-Fi client, plus data capture (encrypt it), on-path attacks (modify/monitor traffic), and DoS via frequency interference.
-
Bluetooth: short-range PAN, used for tethering, headsets, health monitors, auto integration, smartwatches, external speakers.

Wireless Security Settings

-
Wireless network security must cover: authenticating users before granting access (username/password/MFA), encrypting all traffic, and verifying integrity (message integrity check).
-
WPA2 PSK problem: attacker captures the four-way handshake (or derives the hash without it) and brute-forces the pre-shared key offline. Gets easier every year (GPU cracking, cloud cracking). Once the PSK is cracked, every client's traffic on that network is exposed, no forward secrecy.
-
WPA3 (2018) fixes this:
-
Wireless security modes:
ModeAuth
Open SystemNo password
WPA3-Personal / WPA3-PSKShared 256-bit key, everyone uses the same key
WPA3-Enterprise / WPA3-802.1XPer-user authentication against an auth server (RADIUS)
-
AAA framework: Identification (claimed identity, usually a username) -> Authentication (proving it, password + factors) -> Authorization (what that identity is allowed to do) -> Accounting (logging login time, data sent/received, logout time).
-
RADIUS (Remote Authentication Dial-in User Service): common AAA protocol, not just for dial-in anymore. Centralizes auth for routers, switches, firewalls, remote VPN access, and 802.1X network access; runs on nearly any server OS.
-
802.1X: port-based Network Access Control, no network access until authentication succeeds, works with a backing directory like RADIUS, LDAP, or TACACS+.
-
EAP (Extensible Authentication Protocol): an authentication framework, not one method, RFC-standardized but vendors can build their own EAP types. Integrates with 802.1X to gate network access until auth completes.
-
802.1X + EAP roles: supplicant (the client), authenticator (the device granting access, e.g. switch/AP), authentication server (validates credentials, e.g. RADIUS).

Application Security

-
Secure coding is a balance of time vs. quality, security-minded programming is often the thing that slips first. QA testing catches some of it, but vulnerabilities will still surface post-release.
-
Input validation: define expected input up front (forms, fields, type), validate actual input against expected, normalize/correct bad input (e.g. a zip code must be exactly N characters, one letter in a fixed column). Fuzzers exist to find what validation misses.
-
Secure cookies: browser-stored data used for tracking/personalization/session management, not executable and not inherently risky unless someone gets access to it. The Secure attribute forces the browser to only send the cookie over HTTPS. Cookies aren't meant to be secure storage, don't put sensitive data in one.
-
Static code analyzers (SAST): scan source without running it, catches common classes like buffer overflows and injection flaws easily, but misses things like auth logic or crypto misuse. Findings still need human verification, false positives happen.
-
Code signing: developer signs code with their private key (asymmetric), a trusted CA signs the developer's public key (internal apps can use an internal CA). Confirms the code hasn't been modified and came from a known developer.
-
Sandboxing: an app runs isolated, can't touch unrelated resources. Common in development and as a production technique. Implementations: VMs, mobile app sandboxes, browser iframes, Windows UAC.
-
Application security monitoring: real-time usage/access stats, view blocked attacks (SQLi attempts, patched vulns), audit logs for recon/hidden attack activity, anomaly detection (unusual file transfers, spikes in client access).

Asset Management

-
Acquisition/procurement: multi-step purchasing process, request -> budgeting/approvals -> supplier negotiation (terms and conditions) -> purchase/invoice/payment.
-
Assignment/accounting: central asset tracking system used org-wide. Ownership ties a person to an asset (useful for tracking). Classification: hardware = capital expenditure, software = operating expenditure.
-
Monitoring/asset tracking: inventory every device (laptops, desktops, servers, routers, switches, cables, fiber modules, tablets), tie a support ticket to make/model, enumerate all parts of an asset (CPU, RAM, storage, peripherals), tag assets (barcode, RFID, visible ID).
-
Disposal/decommissioning: completely remove data so nothing usable remains. Different needs: wipe a drive for reuse vs. permanently delete one file, it's a one-way trip once done, no forensic recovery.
-
Media sanitization / physical destruction options: shredder/pulverizer (complete destruction), drill/hammer through the platters, degaussing (removes the magnetic field, destroys and disables the drive), incineration.
-
Certificate of destruction: third parties usually handle destruction, get confirmation the data is actually gone, a paper trail of exactly what was destroyed and how.
-
Data retention: back up data (how much, where, versioning, lifecycle, purge old data), driven by regulatory compliance (emails, financial records) and operational needs (accidental deletion, DR). Retention should differ by data type and use case.

Vulnerability Management

-
Not a one-off scan, it's a recurring loop: find assets, scan them, confirm findings are real, rank by risk, hand off to an owner, fix (or apply a compensating control), re-check that the fix actually worked, then report on trends.
-
A "closed" ticket doesn't guarantee the weakness is gone, validation after remediation is the step that actually proves it.

Scan Types

ScanHow it works
AuthenticatedScanner logs into the host, sees deeper config/patch detail
UnauthenticatedScanner only sees what's exposed externally, no credentials
Agent-basedA local agent on the host reports its own vuln data
NetworkSweeps reachable hosts/services from outside
Application scanTargets desktop/mobile app code and behavior
Web application scanTargets software running on a web server
-
Vulnerability scanning itself is usually minimally invasive (unlike a pentest): port scan to see what's open, identify systems and security devices, test from both outside and inside (insider threats count), gather everything, sort signal from noise later.
-
Static analysis (SAST): same tool/limits as under Application Security above, finds common flaw classes fast, needs manual verification, false positives are a known issue.
-
Dynamic analysis (fuzzing): throws random/malformed input at a running app (fault injection, robustness testing, syntax testing, negative testing), watches for crashes/errors/exceptions. Traces back to a 1988 University of Wisconsin class project by Professor Barton Miller (the "Fuzz Generator") studying OS utility reliability. Fuzzing engines are platform/language specific and resource-heavy; CERT (Carnegie Mellon) publishes the Basic Fuzzing Framework (BFF).
-
Package monitoring: apps distributed as packages (especially open source) need supply-chain integrity checks, confirm the source is trusted, no malware added, no embedded vulns, before deployment.

CVE, CVSS, and classification

-
CVE (Common Vulnerabilities and Exposures): cross-referenced public vulnerability catalog (cve.mitre.org), the National Vulnerability Database (nvd.nist.gov) syncs to it. Not everything is definitively identifiable this way, some systems need manual checking once a scanner flags something as possible.
-
CVSS (Common Vulnerability Scoring System): quantitative 0-10 severity score, standards evolve (2.0 vs 3.x scored differently), industry collaborates on feed sharing/automation.
-
Scanner coverage is signature-based, "looks for everything" really means "everything it has a signature for." Keep signatures current or new vulns go undetected.

False Positives / False Negatives

TermMeaning
False positiveScanner flags a vuln that doesn't actually exist (different from a real but low-severity finding)
False negativeA real vuln exists but the scanner missed it
-
Fix: update signatures, and work with the scanner vendor if it's still missing things specific to the environment.

Prioritization

Severity score alone doesn't decide what gets fixed first. Factors that push something up the queue:

-
CVSS score
-
how critical the affected asset is
-
whether it's internet-facing
-
active/known exploitation in the wild
-
public exploit code available
-
sensitive data at risk
-
whether a patch even exists yet
-
other controls already mitigating it
-
business impact if it's hit
-
Exposure factor: percentage of value/business function lost if the vuln is exploited (e.g. a small DDoS limiting access might be a 50% exposure factor, a buffer overflow that fully disables a service is 100%). Worst-case outcome generally wins prioritization ties.
-
Environmental variables: same CVE means different things in different places, internal server vs. public cloud vs. isolated test lab all warrant different patch urgency. Factor in user count (internal/external), whether the app generates revenue, and real exploit potential.
-
Industry/organizational impact: consequences scale with what the org does. Tallahassee Memorial HealthCare ransomware (Feb 2023) closed the facility two weeks, diverted emergency cases, canceled surgeries. Salt Lake City / LA County power utilities (Mar 2019) took DDoS hits from an unpatched known vulnerability.
-
Risk tolerance: zero risk isn't realistic. Patching immediately skips proper testing; testing takes time and leaves the window open. The right timing sits somewhere in the middle and shifts with severity.

Remediation Options

Patching is the obvious one, but not the only lever: upgrade the software, turn off the vulnerable service, fix the insecure setting, tighten access, remove software nobody uses, rotate exposed credentials, or just add monitoring around it as a stopgap.

Reporting

Fields worth including per finding: what was found, which asset, severity, supporting evidence, business impact, recommended fix, assigned owner, due date, current status, and the result once validation is run.

Threat Intelligence

-
Research into threats and threat actors: their tools, group profiles, TTPs. Used to make prevention decisions (where to actually invest), consumed by researchers, SOC teams, and others.
-
OSINT (Open-Source Intelligence): publicly available data, good starting point. Sources: internet discussion groups/social media, government data (public hearings, reports, sites), commercial data (maps, financial reports, databases).
-
Proprietary/third-party intelligence: paying for threat intel someone else already compiled, threat analytics services correlate across many data sources, feed constant monitoring and automated prevention workflows.
-
Information-sharing organizations: public threat intel is often classified, private companies pool resources instead. Cyber Threat Alliance (CTA): members upload formatted threat intel, CTA scores/validates each submission, other members extract the validated data. Real-time, high-quality sharing is the goal.
-
Dark web intelligence: overlay networks needing specific software/config to reach, host hacking group activity, tools/techniques, stolen credit card sales, account/password dumps. Monitor forums for company or executive names showing up.

Penetration Testing

-
Simulates an actual attack, not just scanning: exploits the vulnerability rather than just identifying it. Often a compliance mandate, done regularly by a third party. Reference: NIST's Technical Guide to Information Security Testing and Assessment (SP 800-115).
-
Rules of engagement: the document that defines purpose, scope, and everyone's expectations before testing starts. Covers: type of test and schedule (on-site physical, internal, external; working hours or after-hours only), IP ranges in scope, emergency contacts, how to handle sensitive data found, and explicit in-scope/out-of-scope systems.
-
Environments/types: physical breach testing, internal testing, external testing; offensive (red team, attacking), defensive (blue team, defending/detecting), and integrated (purple team, both sides collaborating) approaches all apply depending on objective.
-
Process: initial exploitation (get in) -> lateral movement (pivot system to system, inside networks tend to be softer targets) -> persistence (backdoors, new accounts, verify default creds still work so there's a way back in) -> the pivot (using a compromised system as a proxy/relay to reach otherwise unreachable systems).
-
Exploiting vulnerabilities: risk of causing real DoS or data loss doing this for real, buffer overflows can crash things, goal is often privilege escalation. May need to chain multiple vuln classes: password brute-force, social engineering, DB injection, buffer overflow. Only bypassing security proves the exposure is real, if the tester can get through, so can an attacker.
-
Responsible disclosure / bug bounty: fixing takes time (code changes, testing, deployment), so disclosure is controlled: researcher reports privately, manufacturer builds a fix, vulnerability gets announced publicly after. Bug bounty programs pay researchers to find and document vulnerabilities instead of exploiting them.

Vulnerability Remediation

-
Patching: most common fix, straightforward when the vuln is known and a patch file exists. Scheduled patch cycles (monthly, quarterly) vs. unscheduled/zero-day patches that need to go out urgently. Ongoing process, patches never really stop.
-
Segmentation: limits blast radius by separating devices into their own networks/VLANs, a breach in one segment doesn't automatically reach everything. Physical segmentation uses separate hardware/infrastructure; logical segmentation with VLANs separates traffic without separate wiring (a Layer 3 device/router is required for cross-VLAN communication). Internal NGFWs can block unwanted east-west traffic and catch malicious internal traffic. Air-gapping (full disconnect) is the extreme version when patching isn't possible.
-
Compensating controls: used when the ideal fix isn't available (no patch yet, no internal firewall). Options: disable the vulnerable service, revoke app access, limit external reach, tighten internal security controls/software firewalls, as coverage until the real fix lands.
-
Exceptions and exemptions: not everything can realistically be patched (needs physical access, local login, breaks something else). An exception is a formal, approved deviation balancing service availability against risk.
-
Cybersecurity insurance: covers costs like lost revenue, data recovery, phishing losses, privacy lawsuits, has grown in popularity alongside ransomware. Doesn't cover everything (intentional acts, funds transfers excluded), applies org-wide.
-
Validation: confirm the patch actually closes the exploit and covers every vulnerable system, then rescan (a full vuln scan, not a spot check).
-
Audit and reporting: check remediated systems actually got the patch, manually verify security where needed. Ongoing/continuous because new vulns never stop appearing; report tracks count of identified vulns, patched vs. unpatched, new threat notifications, and outstanding errors/exceptions/exemptions.

Log Sources & Monitoring

-
Monitoring = pulling in and reviewing activity across hosts, network, apps, cloud, and security tooling so normal vs. abnormal behavior is visible.
-
Common feeds analysts pull from: auth logs, firewall logs, DNS logs, VPN logs, proxy logs, endpoint logs, cloud audit logs, email security logs, web server logs. Investigations lean on the same set plus email headers, file timestamps, and process execution logs.
-
Security monitoring runs 24/7/365, covers every entry point (logins, public-facing services, storage, remote access), reacts to events (account access, firewall rulebase changes, extra scanning), rolls up into status dashboards.
-
Monitoring computing resources: systems (auth from unusual locations, server activity/backups/versions), applications (uptime, response time, data transfer volume, vendor security notices), infrastructure (remote access activity, firewall/IPS attack type and frequency).
-
Scanning is a moving target: new vulns daily, apps/services constantly changing, systems and people constantly moving. Gather OS type/version, driver versions, installed apps, and flag anomalies.
-
Reporting turns raw data into actionable status: patch compliance %, systems on old OS versions, impact assessment when a new vuln drops ("how many systems are exposed"), plus ad hoc summaries for the unexpected.
-
Archiving: average time to identify and contain a breach runs about 9 months (IBM security report, 2022), so long-term log access matters. Archival period is often mandated by state/federal law or internal policy, not just convenience.

Security Monitoring Tools

-
SCAP (Security Content Automation Protocol): NIST-managed specification letting different tools (NGFWs, IPS, vuln scanners) evaluate against the same criteria, validate config, confirm patch installs, scan for breach indicators. Especially valuable in large mixed-OS/mixed-app environments, enables cross-tool automation for ongoing monitoring, alerting, and remediation of noncompliant systems.
-
Benchmarks: apply security best practices/minimum bar to a device type (e.g. mobile: disable screenshots/screen recording, prevent calls while locked, force encrypted backups, disable extra VPN profiles, configure lost-phone messaging). CIS (Center for Internet Security) publishes widely used benchmarks.
-
Agent vs. agentless compliance checks:
MethodBehavior
AgentInstalled software, always monitoring, real-time alerts, more detail, needs maintenance/updates
AgentlessOn-demand check, no formal install, runs then disappears, no ongoing update burden, won't alert if not actively run
-
SNMP (Simple Network Management Protocol): polls devices (servers, firewalls, workstations, switches, routers) at fixed intervals over udp/161, data lives in a MIB (Management Information Base) addressed by OIDs (Object Identifiers), builds historical performance graphs.
-
SNMP traps: instead of waiting to be polled, the monitored device pushes an alert over udp/162 when a threshold is crossed (e.g. CRC error count jumps by 5), gives an immediate reaction instead of waiting for the next poll cycle.
-
NetFlow: gathers traffic statistics across all flows, standard collection method with many vendor implementations. A probe watches network communication and sends summary records to a collector; reporting is usually a separate app tied closely to the collector.
-
Antivirus / anti-malware: "antivirus" historically meant trojans/worms/macro viruses specifically, "malware" is the broader category (spyware, ransomware, fileless malware included). The terms are used interchangeably in practice now, modern AV products are effectively full anti-malware suites.
-
DLP (Data Loss Prevention): finds where sensitive data lives (SSNs, card numbers, medical records) and stops it leaving before an attacker gets it. Usually needs multiple deployment points: endpoint clients, cloud-based systems, email/cloud storage/collaboration tools.

SIEM & SOAR

-
SIEM (Security Information and Event Management): central place logs land, get correlated across sources, searched, and turned into alerts.
-
SOAR (Security Orchestration, Automation, and Response): the layer on top that wires alerts to playbooks, tooling, approval steps, and actual response actions.
-
Orchestration itself just means chaining automated steps across different tools/teams into one workflow, e.g.: SIEM fires an alert -> IP gets auto-enriched -> checked against threat intel -> ticket opens -> analyst gets pinged -> a firewall block gets staged for someone to approve.

Automation

-
Best fit: tasks that repeat often and follow a predictable pattern (parsing logs, building reports, opening tickets, kicking off scans, sending notifications).
-
Security use cases beyond the basics: enriching IPs/domains, disabling compromised accounts, blocking known-bad indicators, pulling endpoint evidence, generating compliance reports, pushing patches.
-
Payoff: quicker response, fewer manual mistakes, consistent process, cleaner evidence trail, less analyst grunt work.
-
Downside: bad logic executes at machine speed too. Automation with more permissions than it needs can do real damage, so high-impact actions (disabling an account, blocking a range) usually still want a human approval gate, and every automated action should be logged and reviewed like any other change.

Firewalls

-
Network-based firewalls: filter by port number or application (traditional vs. NGFW), can encrypt traffic (site-to-site VPN), most operate at layer 3 (routers), handle NAT and dynamic routing.
-
NGFW (Next-Generation Firewall): operates at the OSI application layer (layer 7), also called application layer gateway, stateful multilayer inspection, or deep packet inspection. Every packet gets analyzed, categorized, and a security decision applied, not just port/protocol matching.
-
Ports and protocols: forwarding decisions based on protocol (TCP/UDP) and destination port. Traditional firewalls are port-based only, NGFWs add app-level policy on top. Common pairs: web server tcp/80 tcp/443, SSH tcp/22, RDP tcp/3389, DNS udp/53, NTP udp/123.
-
Firewall rules: evaluated top-to-bottom as a logical path, specific rules sit near the top, general ones lower. Implicit deny sits at the bottom of most firewalls even if never explicitly written. ACLs (Access Control Lists) group rule criteria: source IP, destination IP, port, time of day, application. Rules can be individual or grouped, and get customized per group; balancing tight rules against alert noise/false positives takes time to tune (rule sets can run into the thousands).
-
Screened subnet: an added layer between the internal network and the internet, public resources stay reachable while private data stays inaccessible.
-
IPS (Intrusion Prevention System): usually built into an NGFW, inspects traffic in-line as it passes. Signature-based detection looks for an exact known-bad match; anomaly-based builds a baseline of "normal" and flags deviations. Response options (block, allow, alert) are configurable per rule.

Web Filtering

-
Content filtering: controls traffic based on the data itself (URL filtering, category filtering), enforces corporate policy on outbound/inbound sensitive material, blocks not-safe-for-work content and known-bad sites (AV/anti-malware protection built in).
-
Proxies: sit between users and the external network, receive the request and forward it on the user's behalf. Useful for caching, access control, URL filtering, content scanning. Explicit proxies require app configuration to use them; transparent proxies are invisible to the client. A forward proxy is a centralized internal proxy protecting/controlling outbound internet access.
-
URL scanning: allow/block by URL or URI, managed by category (auction, hacking, malware, travel, recreation, etc.), usually built into an NGFW. Limited on its own since URLs aren't the only way to browse.
-
Agent-based filtering: client software installed on the device itself, filtering decisions happen locally so it works from anywhere, centrally managed, always-on. Updates get pushed to all agents from the cloud, status visible at the console.
-
Block rules: matched against a specific URL (allow/deny by pattern) or a category of site content (50+ categories: adult, educational, gambling, government, home/garden, legal, malware, news, etc.), each category gets its own disposition (allow, allow+alert, block).
-
Reputation-based filtering: URLs classified by perceived risk (trustworthy, low, medium, suspicious, high), automated scanning assigns most reputations, admins can manually override. Dispositions map to the URL filter (e.g. high risk = block, trustworthy = allow).
-
DNS filtering: DNS lookup happens before any connection, so filtering at that layer stops resolution for harmful sites (no IP returned, no connection possible). Threat intelligence lists (commercial and public) keep DNS filters current, applies to any DNS lookup, not just web browsing specifically.

Operating System Security

-
Active Directory: Windows-centric database of everything on the network (computers, user accounts, file shares, printers, groups). Manages authentication (users log in with AD credentials) and centralized access control (who can reach what resource). Commonly used by the help desk for password resets and account changes.
-
Group Policy: manages computers or users via local or domain policies, edited through the Group Policy Management Editor. Provides central control over login scripts, network config (QoS), and security parameters, hundreds of configuration options available.
-
SELinux (Security-Enhanced Linux): adds Mandatory Access Control on top of Linux's traditional Discretionary Access Control, ships as security patches for the kernel. Limits application access on the least-privilege principle so a breach in one app has a limited blast radius. Open source, already an option in most Linux distributions.

Secure Protocols

-
Network traffic is data that needs protection, but plenty of legacy protocols send everything in the clear: Telnet, FTP, SMTP, IMAP. A packet capture is the way to confirm what's actually being sent.
-
Protocol selection: prefer a protocol with encryption built in, if no secure version exists that can be a deal-breaker for a design.
-
Port selection: secure and insecure versions of an app protocol can run on different ports simultaneously, common in the wild.
ApplicationInsecure ProtocolSecure Protocol
Remote consoleTelnetSSH
Web browsingHTTP (port 80)HTTPS (port 443)
Email client accessIMAPIMAPS
File transferFTPSFTP
-
Port number alone doesn't guarantee security, confirm the security features are actually turned on.
-
Transport method: rather than trust the application, encrypt the whole network transport. 802.11 wireless with WPA3 encrypts all user data at the link layer; an open access point has no transport-level encryption at all. A VPN builds an encrypted tunnel so all traffic through it is protected regardless of the app protocol (often needs third-party software/service).

Email Security

-
Email transfer protocols carry relatively few built-in security checks, spoofing a sender address is trivial (check the spam folder, it happens constantly). A reputable sender publishes email validation info publicly on their DNS.
-
Mail gateway: the inbound gatekeeper, evaluates the source of every inbound message and blocks bad ones before they hit the user's inbox, deployed on-site or cloud-based.
-
SPF (Sender Policy Framework): domain owner publishes the list of servers authorized to send mail for that domain in a DNS TXT record, receiving servers check incoming mail against it.
-
DKIM (DomainKeys Identified Mail): mail server digitally signs all outgoing mail, public key published in a DKIM DNS TXT record, receiving server validates the signature (usually invisible to the end user).
-
DMARC (Domain-based Message Authentication, Reporting, and Conformance): extension layered on top of SPF and DKIM. Domain owner decides in a DNS TXT record what receiving servers should do with mail that fails validation (accept, send to spam, reject), and gets compliance reports back showing how mail from the domain is being received/handled.

Monitoring Data

-
FIM (File Integrity Monitoring): watches OS and app files that should never change (or rarely should), flags any modification. Windows uses SFC (System File Checker), Linux commonly uses Tripwire; many host-based IPS tools include this.
-
DLP locations/states:
LocationData state
Workstation (endpoint DLP)Data in use
NetworkData in motion
ServerData at rest
-
USB blocking: DLP agent on the workstation allows/denies removable media use. Notable case: Nov 2008, US DoD banned removable flash media org-wide after the "agent.btz" worm spread via USB, ban lifted Feb 2010 and replaced with strict usage guidelines instead of an outright block.
-
Cloud-based DLP: sits between users and the internet, watches every byte of network traffic with no local hardware/software needed, blocks org-specific custom data strings, manages/limits file transfers to cloud storage, and blocks malware/viruses traversing the network.
-
Email stays the top risk vector for both inbound threats and outbound data loss, check every email in both directions (internal system or cloud-based). Inbound rules block keywords/impersonation attempts and quarantine suspect mail; outbound rules catch things like fake wire transfer requests, W-2 data leaving, or other employee-info leaks. A 2016 case: a Boeing employee emailed a spreadsheet template to a spouse that had hidden columns containing SSNs and DOBs for 36,000 employees, Boeing's own DLP product wasn't applied to that traffic since it was reserved for classified work.

Endpoint Security

-
The endpoint is where the user's access, apps, and data live, needs to stop both inbound and outbound attacks across mobile and desktop. Defense in depth applies here same as anywhere: no single control is enough.
-
Edge control (internet link, firewall rules that rarely change) vs. access control (works from anywhere, rules by user/group/location/app, easily revoked/changed on the fly).
-
Posture assessment: don't trust any device blindly, especially BYOD. Before granting network access, check: is it a trusted/managed device, running AV (which one, updated?), has required corporate apps, is the disk encrypted. Device type (Windows/Mac/Linux/iOS/Android) doesn't change the requirement.
-
Health check delivery methods:
MethodBehavior
Persistent agentPermanently installed, needs periodic updates
Dissolvable agentNo install, runs only during the assessment, terminates after
Agentless NACIntegrated with Active Directory, checks run at login/logoff, can't be scheduled independently
-
Failing the assessment: device gets quarantined (just enough network access to fix the problem), administrators notified, retry once resolved (may need further fixes).
-
EDR (Endpoint Detection and Response): scales beyond signature-based AV. Detect (behavioral analysis, machine learning, process monitoring via a lightweight endpoint agent), investigate (root cause analysis), respond (isolate the system, quarantine the threat, rollback to a known-good config, API-driven with no technician required).
-
XDR (Extended Detection and Response): evolution of EDR aimed at reducing missed detections/false positives/long investigation times since real attacks span more than just the endpoint. Adds network-based detection, correlates endpoint + network + cloud data to improve detection rates and simplify investigations.
-
User behavior analytics: usually bundled into XDR, extends anomaly detection to users/hosts/network traffic/data repositories. Builds a normal-activity baseline over time (rules, pattern matching, statistical analysis), goal is catching unusual activity early.

Identity and Access Management

-
Applications and data live everywhere (desktop, browser, mobile, cloud, private datacenter), and many different populations need access: employees, vendors, contractors, customers. IAM's job: right permissions, right people, right time, preventing unauthorized access.
-
Identity lifecycle management: every entity (human or non-human) gets a digital identity; access control limits each entity to what it needs; authentication/authorization prove and enforce claimed identity; identity governance tracks resource access over time (often a regulatory requirement).
-
Provisioning / de-provisioning: account creation and removal processes, triggered by hiring, transfers, promotions, and separation events. Provisioned accounts carry name, attributes, group permissions; new accounts should start limited, nobody gets administrator by default.
-
Identity proofing: confirming who someone actually is before granting an identity. Resolution (who the system thinks the person is), validation (gathering proof: password, security questions), verification/attestation (passport check, in-person meeting, or automated verification).
-
SSO (Single Sign-On): authenticate once, get access to every resource that trusts the SSO session without re-entering credentials, usually time-boxed (e.g. 24 hours before re-auth is required). Needs the underlying auth infrastructure to actually support it, not always available.
-
LDAP (Lightweight Directory Access Protocol): protocol for reading/writing directory data over IP, structured like a phone directory. Based on the X.500 spec (International Telecommunications Union) but lightweight compared to X.500's DAP (which ran on the full OSI stack). Used to query/update directories like Active Directory, Apple OpenDirectory, Novell eDirectory. X.500's Directory Information Tree is hierarchical: container objects (country, org, org unit) hold leaf objects (users, computers, printers, files).
-
SAML (Security Assertion Markup Language): open standard for authentication and authorization through a third party, one standard covering identity + access decisions. Wasn't originally built for mobile apps, which has limited its mobile adoption.
-
OAuth: an authorization framework (not authentication), decides what resources a user can access once identity is established. Built by Twitter/Google and widely adopted (Twitter, Google, Facebook, LinkedIn). OpenID Connect is the companion piece that actually handles SSO-style authentication; OAuth itself just governs authorization between apps.
-
Federation: extends access beyond employees to partners, suppliers, customers, provides SSO across organizational boundaries ("login with Facebook" is federation in consumer form). Requires a trust relationship (and an agreed degree of trust) between the two orgs.
-
Interoperability: many ways an app can talk to an auth server, driven by what's already in place (a VPN concentrator talking LDAP, a new app needing OAuth API access). Fitting a new app into existing IAM infrastructure is often a bigger design question than the auth method itself.

Access Controls

-
Authorization: enforcing only the rights a policy grants, based on the access control model chosen and business/mission requirements.
-
Least privilege: rights/permissions set to the bare minimum needed for the job, applications should run with minimal privileges too, users shouldn't run with admin rights day to day, limits how much damage malicious activity can do.
ModelHow access is decidedNotes
MAC (Mandatory Access Control)OS enforces access based on security labels (confidential, secret, top secret) on every objectAdmin sets the level, users can't change it
DAC (Discretionary Access Control)Object owner decides who gets accessDefault in most OSes, very flexible, but weak security since the owner can grant access at will
RBAC (Role-Based Access Control)Access follows organizational role (manager, team lead, project manager)Windows Groups implement this, rights gained implicitly through role membership
Rule-based access controlSystem-enforced rules tied to the object, not the requester's identitye.g. lab access only 9AM-5PM, only Chrome browsers may submit a form; admins configure, users can't override
ABAC (Attribute-Based Access Control)Evaluates many parameters at once (resource info, IP, time of day, action requested, relationship to the data)"Next-generation" model, context-aware, handles complex user-to-resource relationships
-
Time-of-day restrictions: nearly all security devices support this, restricts access by time/day but is rarely the only control in play. Harder to apply cleanly in 24-hour environments. Example rules: training room network dead midnight-6AM, conference room access cut off after 8PM, R&D database only reachable 8AM-6PM.

Multifactor Authentication

-
Proving identity by combining multiple factor categories, not just stacking two things from the same category.
FactorExamples
Something you knowPassword/passphrase, PIN, pattern
Something you haveSmart card (may need a PIN), USB security key (cert on the device), hardware/software token generating pseudo-random codes, SMS code to phone
Something you areBiometric: fingerprint, iris scan, voice print (usually stores a mathematical representation, not the raw print, hard to change if compromised, not foolproof)
Somewhere you areLocation-based factor: IP address (imperfect, weaker on IPv6), mobile geolocation via GPS/known network (not a perfect identifier either)
-
A PIN isn't typically stored anywhere on the card/token itself, it has to be something the user separately knows.

Password Security

-
Complexity/length: resist guessing and brute-force by mixing case, numbers, special characters, avoiding single dictionary words. Entropy matters more than a fixed rule; 8+ characters is a common floor and rises as cracking speed improves. A passphrase can substitute for pure complexity.
-
Age and expiration: password age = time since last change; expiration forces a change after a set window (30/60/90 days), critical systems may rotate weekly or every 15 days. Systems typically track password history to block immediate reuse.
-
Password managers: store every credential in one encrypted vault so users aren't reusing weak passwords out of necessity, can include MFA tokens too. Built into many OSes/browsers already; enterprise password managers add centralized management and recovery.
-
Passwordless authentication: most breaches trace back to poor password hygiene (weak passwords, bad implementation), so removing the password removes that failure class. Facial recognition and hardware security keys are common passwordless factors, though passwordless is often paired with another factor rather than standing entirely alone.
-
Just-in-time (JIT) permissions: standing admin/root rights are a prime attack target. JIT grants elevated access only for a limited window instead of permanently, requested through a central clearinghouse that grants/denies against predefined policy; a breached account with no standing elevated rights has a much narrower blast radius.
-
Password vaulting: primary credentials for privileged accounts are stored in a vault that controls who can check them out. Access is temporary: JIT creates an ephemeral account, the admin receives one-time credentials, the primary password is never actually revealed, and access is deleted after the session ends.

Scripting and Automation

-
Automation runs at machine speed with no typing, no delay, no human error, and it doesn't need to be told twice, it works while nobody's watching.
-
Common cases: user/resource provisioning (onboarding/offboarding, resource assignment), guard rails (automated validations that constantly check implementation and cut errors), security group membership changes with constant audit trails, automatic ticket creation from identified issues or email submissions, escalation (correct issues before a human gets pulled in, page the on-call tech if unresolved), enabling/disabling services and access on a schedule instead of "set and forget," continuous integration/testing, and API-driven integrations with third-party devices/services (cloud, firewalls, other OSes).
-
Benefits: no manual typing, enforces baselines automatically (patches installed the moment they're identified), standardizes infrastructure config (a script builds the same secure router/firewall config every time), secures cloud scaling (security scales along with resource scaling instead of lagging behind), frees staff from repetitive work (retention benefit), reaction time drops to machine speed, and it multiplies the workforce (runs 24/7 so people can do higher-value work).
-
Considerations/risks: complexity (many moving parts that all have to keep working together), cost (building and maintaining automation both cost money), single point of failure (what happens when the script itself breaks, could be a real deal-breaker), technical debt (patching around a problem now can get more expensive to properly fix later), and ongoing supportability (a script that works today may not work tomorrow, needs a maintenance plan).

Alerting

-
An alert just flags activity that might need a human to look at it, sourced from SIEM, EDR, IDS/IPS, firewall, cloud tooling, or email security.
-
A well-formed alert carries: name, severity, user, host, IP, timestamp, which log it came from, why it fired, and suggested next steps for triage.
-
Recurring alert scenarios: repeated failed logons, a successful login right after a string of failures, impossible-travel logins, malware hits, suspicious PowerShell activity, a new admin account appearing, public exposure of cloud storage, unusually large outbound transfers.

Tuning

Adjusting alert logic so it fires on the right things and stays quiet otherwise, via thresholds, allow lists, suppression windows, factoring in asset criticality/user context, or correlating with related alerts. Point is cutting false positives before they burn out an analyst.

Triage

First questions on any alert: what actually triggered it, is this expected behavior for that user/system, who and what is involved, what happened immediately before and after, does this need containment right now.

Incident Response Process

Structured process exists so people aren't improvising under pressure.

PhaseWhat happens
PreparationPlaybooks written ahead of time, contact lists current, logging in place, tools ready, access permissions sorted, backups tested, staff trained, tabletops run
Detection & AnalysisConfirm the alert is a real incident, figure out who/what/where is affected, start building a timeline
ContainmentStop it from spreading: disable the account, isolate the endpoint, block the IP/domain, pull the box off the network, kill the leaked API key
EradicationRemove the actual cause: strip out malware, patch the exploited hole, delete persistence mechanisms, rebuild the box, remove rogue accounts
RecoveryGet back to normal: restore from backup, reconnect the cleaned system, force credential resets, watch for a repeat, confirm the business service actually works again
Lessons LearnedPost-incident review: root cause, timeline, impact, what was done, what should change next time
-
Detection/analysis questions worth asking every time: what happened, when, which assets, is the attacker still in there, what evidence backs the conclusion.
-
Evidence and documentation matter at every phase, not just at the end.
-
This process traces to NIST SP800-61 Rev. 2 ("Computer Security Incident Handling Guide").
-
The challenge of detection: sources vary in detail/perception, incoming volume is constant, incidents are almost always complex enough to need real analysis rather than a quick glance. Signals worth watching: web server logs showing scanner activity in use, exploit announcements (a monthly patch release, an Adobe update implying a known flaw), and direct threats from a hacking group.
-
Preparing for an incident ahead of time: communication methods and contact lists ready, incident handling hardware/software staged (laptops, removable media, forensic tools, cameras), analysis resources on hand (documentation, network diagrams, baselines, known-good file hashes), mitigation software ready (clean OS/app images), and clear policy so everyone already knows their role.
-
Isolation and containment: letting an incident run its course is generally the wrong call, it spreads fast and containment failure is on the responder. Sandboxes give an isolated OS to detonate and analyze malware safely, wiped after use. Isolation can backfire though, some malware monitors its own connectivity and triggers destructive action (deletion/encryption) the moment it senses it's cut off.
-
Recovery: remove the bad, keep the good. Eradicate (remove malware, disable breached accounts, fix the underlying vulnerabilities), recover (restore from backup, rebuild from scratch, replace compromised files, tighten the perimeter on the way back up).
-
Lessons learned: no system is perfect, hold a post-incident meeting with everyone affected, don't wait too long, memories fade and by-then-irrelevant details get lost. Answer directly: what happened (timestamped), did the incident plan actually work, what would be done differently next time, which indicators/precursors deserve closer watching going forward.
-
Training: little of this can be learned on the job mid-incident, train ahead of time on initial response, investigation planning, and incident reporting. Can get expensive fast with larger response teams.

Incident Planning

-
Exercising: test the team before a real event happens, on a defined schedule (annual, semi-annual), with well-defined rules of engagement that keep hands off production systems, a specific limited-time scenario, then evaluate and document the response afterward.
-
Tabletop exercises: a full-scale disaster drill is costly and time consuming, a tabletop gets key players in a room to talk through a simulated disaster instead, most of the logistics can be worked out analytically without physically running the drill.
-
Simulation: test against a simulated event (phishing attack, password reset requests, staged data breach). A phishing simulation sends a crafted phishing email to the real user community to see who clicks, whether it got past the filter in the first place, and whether flagged users need more training.
-
Root cause analysis: chase the actual "why" behind an incident, not just its symptom, build a fact-backed set of conclusions. Avoid tunnel vision, more than one root cause is common. Mistakes will happen, the response to the mistake is what actually differentiates a mature program.
-
Threat hunting: a constant cat-and-mouse game, proactively finding the attacker before they find the org. Attacker strategies keep shifting as defenses improve (stronger firewalls push more effort into phishing, for instance). Standard intel is reactive by nature, hunting is the attempt to get ahead of that lag using technology to speed up reaction time.

Digital Forensics / Investigating an Incident

-
Investigation = evidence-driven reconstruction of what happened, how, what got touched, and what needs to happen next. Assumptions don't substitute for evidence.
-
Evidence pool overlaps heavily with the log sources list above, plus email headers, file timestamps, EDR alerts, and process execution history.
-
Standard forensic process: acquisition, analysis, reporting, all of it detail-oriented with extensive notes. RFC 3227 ("Guidelines for Evidence Collection and Archiving") is a widely referenced best-practices baseline.

Timeline

Chronological record of events around the suspicious activity. Useful fields per entry: timestamp, source, user, host, IP, the event itself, analyst notes.

Sample sequence:

-
10:03 - repeated failed logins from an external IP
-
10:08 - login succeeds
-
10:12 - a new mailbox forwarding rule gets created

Scope

Boundaries of what got hit. Questions to work through: single user or several, single host or several, was sensitive data touched, was there a privilege escalation attempt, is the attacker still active, are there related alerts elsewhere.

Root Cause

The actual reason the incident happened, not just the symptom. Common ones: stolen credentials, a missing patch, misconfigured cloud storage left open, a phishing email that landed, a weak password, an exposed remote access service.

Legal hold and chain of custody

-
Legal hold: a legal technique to preserve relevant information ahead of impending litigation, initiated by legal counsel. Hold notification instructs custodians to preserve data; electronically stored information (ESI) usually gets its own repository with its own retention/workflow requirements. Once notified, the obligation to preserve is ongoing, it doesn't lapse after the initial collection.
-
Chain of custody: controls evidence to maintain its integrity. Everyone who touches the evidence gets logged (hashes and digital signatures help prove no tampering occurred), and everything gets labeled/cataloged, digitally tagged for ongoing documentation, then sealed and stored.
-
Acquisition: obtaining the actual data, which can span disk, RAM, firmware, OS files, and sources beyond a single system (servers, network data, firewall logs). For virtual systems, a snapshot captures the entire VM state and its files at once. Also look for left-behind artifacts: log info, recycle bins, browser bookmarks, saved logins.
-
Preservation: isolate and protect evidence so it can be analyzed later without alteration, work from copies rather than originals, and manage the collection process for mobile devices specifically. Live collection (grabbing data before power-off) has become an important skill since data may be encrypted or unrecoverable once a device is powered down. Following best practices here is what keeps the data admissible in court later.
-
Reporting: document findings for internal use or legal proceedings, cover summary info (overview of the event), a detailed step-by-step explanation of the data acquisition process, the findings themselves, and a conclusion presenting professional results given the analysis.
-
E-discovery (electronic discovery): the process of collecting, preparing, reviewing, interpreting, and producing electronic documents required by a legal process. Gathers what's needed without generally analyzing intent, works alongside digital forensics (e.g. e-discovery obtains a drive that turns out smaller than expected, forensics experts then determine data was deleted and attempt recovery).

Log Data

-
Firewall logs: traffic flows through the firewall (source/destination IP, port numbers, disposition). NGFWs additionally log the application in use, URL filtering categories, and flagged anomalies/suspicious data.
-
Application logs: content varies widely by app. Windows keeps these in Event Viewer's Application Log; Linux/macOS write to /var/log. Parse and filter out the noise before it hits the SIEM.
-
Endpoint logs: attackers frequently land on endpoints first (phones, laptops, tablets, desktops, servers), so there's a lot of relevant data here: logon events, policy changes, system events, process execution, account management, directory service activity. All of it rolls up to the SIEM, correlated with IPS events and endpoint status.
-
OS-specific security logs: monitoring apps, brute-force attempts, file changes, authentication details. Goal is catching problems before they happen (brute-force attacks, disabled services), may need filtering so the SIEM isn't flooded with everything.
-
IPS/IDS logs: usually built into an NGFW, log info tied to predefined vulnerability signatures (known OS vulns, generic security events). Common fields: timestamp, attack type/class, source and destination IP, source and destination port.
-
Network logs: switches, routers, access points, VPN concentrators, and other infra devices logging routing updates, authentication issues, and network security events.
-
Metadata: data describing other data. Email metadata includes header details, sending servers, destination address. Mobile metadata includes phone type and GPS location. Web metadata includes OS, browser type, IP address. File metadata includes name, address, phone number, title fields embedded in the document itself.
-
Vulnerability scan logs: flag lack of security controls (no firewall, no AV, no anti-spyware), misconfigurations (open shares, guest access enabled), and real vulnerabilities (mostly newer ones, occasionally old unpatched ones still lingering).

Automation & Orchestration Risks

Worth repeating separately from the benefits above: wrong logic in an automated playbook fires wrong actions just as fast as right ones, and automation running with more access than it needs turns a small mistake into a bigger one. Keep high-impact actions behind an approval step, and log/test/review automated actions the same as any manual change.
