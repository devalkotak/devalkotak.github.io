SY701 Notes - 5. Security Program Management & Oversight

2026-08-19Notes

Security Policies

-
Policy sets the "what" and "why" (CIA framing: confidentiality, integrity, availability); technical controls handle the "how".
-
High-level strategy: data storage rules, security event handling. Detailed goals sit underneath: acceptable Wi-Fi use, remote access requirements.
-
Information security policy: the master catalog of every security-related policy an org runs, a centralized reference tied to compliance requirements and roles/responsibilities. Only useful if actually enforced.
-
AUP (Acceptable Use Policy): defines acceptable use of company assets (internet, phones, computers, mobile devices), often folded into the employee handbook or Rules of Behavior. Limits legal liability and documents grounds for dismissal.
-
Business continuity policy: fallback for when systems fail (manual transactions, paper receipts, phone-based approvals). Has to be documented and tested before a real disruption hits, not during one.
-
Disaster recovery plan: IT-specific piece of business continuity, covers natural disasters, tech/system failures, human-caused incidents. Comprehensive plan spells out recovery location, data recovery method, application restoration order, IT/employee availability.
-
Security incident examples: user executes malware from an email attachment that then calls out to external servers, DDoS via botnet, data theft for extortion or public leak, P2P software accidentally exposing internal access.
-
Incident response roles: incident response team (trained, tested specialists), IT security management (corporate support), compliance officers (regulatory knowledge), technical staff (in the trenches), user community (first to spot something off).
-
NIST SP 800-61 incident handling lifecycle: preparation, detection and analysis, containment/eradication/recovery, post-incident activity.
-
SDLC (software/systems development life cycle): no single "right way" to go from idea to shipped app, but a framework helps balance customer requirements, schedule, and budget.
-
Change management: covers how a change gets made (software upgrade, firewall config change, switch port change). One of the most common risk sources in an enterprise, frequently skipped or rushed. Needs clear policy on frequency, duration, install process, fallback procedure.

Security Standards

-
Standard = formal, mandatory spec for applying a security technology or process. More prescriptive than a policy's high-level direction. Complete documentation cuts risk because everyone works from the same expectations.
-
May be written in-house (org-specific requirements) or adopted from an existing body (ISO, NIST).
-
Password standard: complexity requirements, approved authentication methods (e.g. LDAP-only, no local accounts), secure reset workflow that avoids unauthorized resets, change frequency, storage requirements, password manager guidance.
-
Access control standard: defines which data, at what time, under which circumstances access is granted. Specifies the access control model in use (discretionary, mandatory, etc.), documents how privilege is granted, and how it's removed (termination, expiration, contract renewal).
-
Physical security standard: rules for building/door access and property security, different procedures for employees vs visitors, electronic locks, ongoing monitoring, motion detection, mandatory escorts, ties into offboarding.
-
Encryption standard: algorithm and implementation requirements for securing data, password storage method, minimum encryption requirements for data at rest, in transit, and in use (often different per state).

Security Procedures

-
Change control: the formal process wrapped around change management to avoid downtime, confusion, mistakes. Steps: scope the change, analyze the risk, build a plan, get end-user approval, present to the change control board, have a backout plan ready, document the result.
-
Onboarding: create accounts tied to the right groups/departments, get the AUP/IT agreement signed (often bundled into the employee handbook), issue preconfigured hardware.
-
Offboarding: should be pre-planned rather than figured out on the spot. Covers what happens to hardware, what happens to data, and account deactivation (deactivated isn't always the same as deleted).
-
Playbooks: conditional, step-by-step process for a given scenario (data breach investigation, ransomware recovery). Works as a manual checklist or feeds a SOAR (Security Orchestration, Automation, and Response) platform to automate the response and pull in third-party tools/data.
-
Procedures need ongoing monitoring and revision: shifts in security posture tighten change control and add playbooks, an update to one procedure ripples into related playbooks, new threats prompt new checks.
-
Governance structures: boards (panel of specialists, gathers info for a committee), committees (make the actual decisions, weigh board input), government entities (bring legal, administrative, and political constraints, often open to public records), centralized governance (decisions made from one location/group) vs decentralized (spread across multiple individuals or locations).

Security Considerations

-
Regulatory: security processes like logging, data storage, protection, and retention usually exist as a foundational response to a regulation. SOX (Sarbanes-Oxley Act, 2002) governs accounting/financial reporting integrity. HIPAA sets healthcare data storage, use, and transmission standards.
-
Legal: security teams often carry legal duties, reporting illegal activity, preserving data under legal hold. Breach notification is a legal requirement in many jurisdictions. Cloud data moving across jurisdictions without human intervention makes this harder to track.
-
Industry: requirements vary by vertical. Utilities need isolated, protected control systems. Medical needs tightly secured data storage, access logging, and encryption.
-
Geographical scope: local/regional (city/state government records, uptime of end-user services), national (federal defense concerns, multi-state coordination, protecting state secrets), global (multinational operations, global financial markets, legal requirements varying widely by country).

Data Roles and Responsibilities

-
Data roles are organizational assignments, not always technical ones.
-
Data owner: accountable for a specific data set, usually a senior officer (VP of Sales owns customer relationship data, Treasurer owns financial data).
-
Data controller: decides the purpose and means by which personal data gets processed.
-
Data processor: processes data on the controller's behalf, often a third party or separate group.
-
Data custodian/steward: hands-on role, responsible for data accuracy, privacy, and security day to day. Applies sensitivity labels, keeps processing compliant with applicable law/standards, manages access rights, implements the actual security controls.

Risk Management Concepts

-
Risk management = identify, analyze, prioritize, treat, monitor. Goal isn't zero risk, it's getting risk down to a level leadership can live with.
-
Used to triage: what gets fixed now, what waits, what needs sign-off from above.

Core building blocks:

-
Asset: anything worth protecting (data, servers, laptops, accounts, cloud storage, apps, business processes).
-
Threat: anything capable of causing harm, disclosure, disruption, or loss.
-
Vulnerability: a weakness a threat can exploit.
-
Risk: the chance a threat actually exploits that weakness and hurts an asset or the org.

Worked example: payroll server (asset) + external attacker (threat) + unpatched CVE (vulnerability) = attacker pulls payroll data (risk realized).

Likelihood vs impact:

-
Likelihood: how probable the event is.
-
Impact: how bad it gets if it happens, covers financial loss, downtime, data loss, legal/regulatory fallout, reputation damage, safety.
-
High likelihood + high impact = top priority. Low + low = candidate for acceptance or just watching it.

Risk categories:

-
Inherent risk: what's there before any controls are applied.
-
Residual risk: what's left over after controls are applied. (Turning on MFA cuts account-compromise risk, doesn't zero it out, the leftover is residual.)
-
Control risk: the chance a control itself fails or doesn't work as designed.
-
Risk appetite: how much risk the org says it's willing to carry, in general.
-
Risk tolerance: how far actual risk can drift from that appetite before it's a problem, usually a larger acceptable variance than the appetite itself (like a speed limit: the posted number is the appetite, how far over it before a ticket gets written is the tolerance, and it can shift with conditions).
-
Risk threshold: the cost of mitigating a risk should be at least equal to the value gained by mitigating it, otherwise the fix costs more than the problem.

Assessment cadence:

-
Ad hoc: no formal recurring process, run when a situation demands it (e.g. leadership wants a check after a new attack type makes news). A committee stands up for the assessment and disbands after, no need to revisit unless something changes.
-
Recurring: runs on a set interval, could be internal (quarterly) or mandated by a regulation (PCI DSS requires annual risk assessments).
-
Continuous: baked into an existing process, e.g. change control requiring a risk assessment as part of every change.

Risk register additions:

-
Key risk indicators (KRIs): metrics tracked to flag risks that could impact the org, each one assigned a risk owner to manage it.
-
Asset value (AV): dollar value of the asset to the org, including replacement cost and downstream effects like lost sales or regulatory fines.
-
Exposure factor (EF): percentage of asset value lost in a single incident (0.25 = quarter of the value lost, 1.0 = total loss).
-
SLE = AV x EF. Example: $1,000 laptop (AV) stolen outright (EF 1.0) = $1,000 SLE.

Risk Response

StrategyWhat it meansExample
AcceptAcknowledge and monitor, no further actionLow-severity finding on a non-critical internal box
AvoidKill the activity that creates the riskDecommissioning an unsupported public-facing service
TransferPush responsibility or cost to a third partyCyber insurance, outsourcing with contractual security terms
MitigateCut likelihood or impact via controlsPatching, MFA, encryption, segmentation, backups

Acceptance has two special-case flavors:

-
Exemption: a security policy or regulation genuinely can't be followed (limited by available controls, org size, asset type), needs formal sign-off to waive it.
-
Exception: an internal policy isn't applied in a specific case (e.g. policy says patches within 3 days, but a patch crashes a critical package, so an exception extends the timeframe).

Risk reporting: formal document built for senior management, lists identified risks with supporting detail so leadership can decide on resourcing, budget, and priority. Usually leads with the critical and emerging risks.

Risk register: the tracking document, one row per risk, capturing risk ID, affected asset/system, description, threat, vulnerability, likelihood, impact, rating, existing controls, recommended treatment, owner, due date, status. Gives the team a shared, trackable view of what's outstanding.

Risk analysis, two approaches:

-
Qualitative: descriptive buckets (low/medium/high).
-
Quantitative: dollars and probabilities.

Business Impact Analysis (BIA): maps out which business functions matter most and what disruption costs, feeds recovery prioritization. Key terms:

-
RTO (Recovery Time Objective): max acceptable time to get a system back up.
-
RPO (Recovery Point Objective): max acceptable data loss, measured in time.
-
MTD (Maximum Tolerable Downtime): the outer limit before an outage becomes existential.
-
MTTR (Mean Time to Repair): average time to fix an issue, including diagnosis time. Key input for costing unplanned outages.
-
MTBF (Mean Time Between Failures): average time between outages (total uptime / number of breakdowns), used as a historical-performance-based prediction for planning around future failures.

Third-Party Risk

Third-party risk = exposure created by anyone outside the org touching business operations: cloud providers, payroll vendors, MSPs, software vendors, data processors, contractors, hardware suppliers. Any access they get (systems, data, network, physical space) inherits their security posture as a weak link.

Supply chain risk is the broader version: risk baked into the products, software, hardware, and subcontractors an org depends on. Attackers go after the trusted vendor relationship instead of hitting the target directly. Examples: poisoned software update, vulnerable third-party library, compromised vendor account, insecure API integration, malicious code slipped into a dependency, cloud provider outage.

Supply chain analysis: evaluates the full path a product/service takes from supplier to customer, checks coordination between groups, identifies improvement areas, assesses the IT systems supporting the operation, documents process changes. Case study: SolarWinds, malware inserted into a signed software update between March and June 2020, announced December 2020, at least 18,000 of 300,000 customers potentially exposed to a compromise that carried a valid digital signature.

Vendor selection: due diligence checks a company out before doing business (financial status, pending/past legal issues, background checks, personnel interviews). Watch for conflict of interest: a potential partner also serving a top competitor, a vendor employing a relative of a decision-maker, a vendor offering gifts tied to signing a contract.

Right-to-audit clause: contract language giving the org the legal option to perform a security audit of the vendor at any time, agreed to by both sides up front. Matters most with partners handling shared data or outsourced processing, so security can be verified before a breach forces the question.

Independent assessments: bringing in an outside specialist firm to evaluate security and provide recommendations. Their value is doing this work full-time across many orgs, so they've seen options an internal team might not have considered.

Questionnaires: a due diligence and ongoing-monitoring tool, gets answers straight from the vendor (due diligence process, DR plans, data storage method, and more). Results feed back into updating the vendor risk analysis throughout the relationship, not just at signing.

Vendor due diligence, before signing anything, check for:

-
Security questionnaire responses
-
SOC 2 report
-
ISO 27001 certification
-
PCI DSS / HIPAA compliance evidence where relevant
-
Data handling and encryption practices
-
Access control and incident response processes
-
BC/DR plan
-
Vulnerability management process
-
Subcontractor list (fourth-party exposure)

Contracts and SLAs should nail down: data ownership, breach notification window, audit rights, encryption requirements, logging/monitoring expectations, uptime commitments, RTO/RPO, termination rights, and secure data return or destruction on exit. SLA = the document that spells out expected service performance.

Vendor access control:

-
Least privilege, time-boxed where possible.
-
Named accounts over shared credentials, MFA required.
-
Restrict by time window, source IP, role.
-
Log everything vendors touch, review privileged access on a schedule.

Vendor relationships need ongoing monitoring, not a one-and-done review at signing: annual reassessment, periodic access reviews, contract renewal checks, incident notification review, compliance report refresh, watching for breach news about the vendor.

Offboarding a vendor matters because stale access is a lingering hole: disable accounts, revoke API keys/tokens, pull VPN/remote access, get company assets back, confirm data was deleted or returned, update the documentation, pull logs if there's any question.

Third-party penetration testing is often a compliance mandate rather than optional, may also be a legal requirement in some contracts. Rules of engagement defines purpose and scope so every party knows the test parameters: type of test and schedule (on-site physical breach, internal, external, business-hours only vs after-hours), in-scope IP ranges, emergency contacts, how sensitive info gets handled, in-scope and out-of-scope devices/applications.

Governance & Compliance

Governance: how an org steers, controls, measures, and improves its security program. Sets who owns risk decisions, who signs off on policy, how exceptions get handled, and how performance gets reported up. Ties security work back to business objectives rather than letting it run as its own silo.

Compliance: following the laws, regulations, contracts, standards, and internal policies that apply. Doesn't guarantee an org is actually secure, but it builds accountability and creates a paper trail. Common compliance areas: privacy law, card data (PCI DSS), healthcare data (HIPAA), financial data, security awareness training requirements, access review cadence, incident reporting obligations.

Governance document hierarchy:

TypePurposeExample
PolicyHigh-level management direction"All users must protect company data"
StandardSpecific, mandatory requirement"Passwords must be 14+ characters"
ProcedureStep-by-step how-toSteps to disable an account during offboarding
GuidelineRecommended, not mandatory"Use a password manager"
BaselineMinimum approved configurationWindows workstation hardening baseline

Typical named policies an org maintains: acceptable use, password, access control, data classification, remote access, incident response, change management, backup, vendor risk, mobile device.

Control ownership: every control needs a named owner accountable for implementing it, keeping it running, producing evidence, and improving it over time. Split usually looks like: HR owns onboarding/offboarding steps, IT owns patching, security owns SIEM rules, management owns risk acceptance decisions.

Compliance evidence (proof a control is actually operating): policy/procedure docs, access review exports, config screenshots, audit logs, vulnerability scan reports, patch reports, backup test results, awareness training completion records, incident response records.

Frameworks and regulations that come up repeatedly: NIST Cybersecurity Framework, ISO 27001, SOC 2, PCI DSS, HIPAA, GDPR, CIS Controls, SOX, GLBA (Gramm-Leach-Bliley Act, 1999, governs disclosure of privacy info by financial institutions).

Compliance reporting splits internal vs external:

-
Internal: monitors and reports on the org's own compliance effort, large orgs often name a Central Compliance Officer (CCO), also used to brief customers or investors.
-
External: documentation required by regulators or industry bodies, may need annual or ongoing reporting, missing or invalid reporting risks fines/sanctions.

HIPAA non-compliance penalties scale with intent, from civil fines (up to $100/violation, capped at $25,000/year for an identical violation) up through felony tiers for false pretenses ($100,000 fine, up to 5 years) and intent to sell/use health data for gain ($250,000 fine, up to 10 years).

Consequences of non-compliance go beyond fines:

-
Reputational damage: disclosure requirements mean a breach often becomes public, stock price can take a short-term hit. Case study: Uber's October 2016 breach exposed 25.6 million names/emails/phone numbers, wasn't disclosed until November 2017, the company paid the attackers $100,000 and had them sign an NDA instead of reporting it, then paid $148 million in fines in 2018; the attackers pleaded guilty in 2019 and Uber's former CSO was sentenced in May 2023 to three years probation plus a $50,000 fine.
-
Loss of license: a significant economic sanction, the org can't sell its product and others can't legally buy from it, re-licensing can be costly.
-
Contractual impacts: some deals require a minimum compliance level, falling below it puts the contract in breach, resolvable with or without going to court.

Compliance monitoring keeps day-to-day operations aligned with requirements:

-
Due care: acting honestly and in good faith, tends to describe internal activities.
-
Due diligence: investigating and verifying before acting, tends to describe activities tied to a third party.
-
Attestation and acknowledgment: someone formally signs off on compliance documentation and is ultimately accountable if it turns out incorrect.
-
Automation is close to mandatory at scale: monitoring tools differ across vertical markets, collect data from people and systems, compile it into reports.

Privacy

-
Privacy guidance is a constantly shifting set of rules, scoped locally/regionally (state/local privacy limits, vehicle registration, medical licensing), nationally (HIPAA, children's online privacy under 13), and globally (multiple countries coordinating on privacy standards).
-
GDPR (General Data Protection Regulation): EU regulation covering data protection and privacy for individuals, applies to name, address, photo, email, bank details, social media posts, medical info, even a computer's IP address. Controls export of personal data, gives data subjects a right to be forgotten (removal from search engines and, where applicable, deletion), lets users decide where their data goes.
-
Data subject: any identified or identifiable natural person, defined broadly (name, ID number, address, genetic makeup, physical characteristics, location data). Privacy is written from the data subject's perspective, not the org's.
-
Data inventory and retention: document what data the org stores, who owns it, how often it updates, and its format. Internal use covers project collaboration, security work, quality checks; external use means selecting what's safe to share publicly under existing law/regulation.

Audits & Assessments

Audit: formal check on whether controls, policies, procedures, standards, regulations, or contract terms are actually being followed. Can be internal or external, may originate findings that require remediation. Goals: verify compliance, confirm controls actually operate, surface gaps, back up regulatory requirements, produce evidence for leadership or customers.

Assessment: broader review aimed at understanding risk, control effectiveness, technical weaknesses, or overall posture, generally more improvement-oriented than an audit's compliance focus.

Assessment typeWhat it checks
Risk assessmentIdentifies and ranks risks
Vulnerability assessmentFinds and prioritizes technical weaknesses
Penetration testActively exploits weaknesses to prove real impact
Configuration reviewCompares systems against secure baselines
Access reviewChecks whether granted permissions are still appropriate
Tabletop exerciseWalks a scenario to test response decision-making
Compliance assessmentChecks alignment against a standard/regulation

Evidence backs up both audits and assessments: policy/procedure docs, config screenshots, access review exports, vuln scan reports, patch reports, backup test results, log samples, incident reports, training completion records.

Findings: a documented issue from an audit/assessment, should include description, affected system/process, supporting evidence, risk/impact rating, recommendation, owner, due date, status.

Remediation tracking: findings stay open until proven fixed, not just marked closed on someone's word. Example: finding is "local admin rights too broad," recommendation is "remove unneeded local admin," closure evidence is an updated group membership export plus access review sign-off.

Cybersecurity audit examines IT infrastructure, software, and devices, checks whether policies/procedures are actually effective, aims to find vulnerabilities before attackers do. Can run internally or via a third party.

Attestation: an opinion on the truth or accuracy of an org's security posture, an auditor formally attests to what they found.

Internal audits: not just for third-party relationships, orgs run these on themselves to check regulatory/industry compliance. An audit committee oversees risk management activity and owns the audit lifecycle start to finish. Self-assessments (the org checking its own work) roll up into ongoing reports.

External audits: often triggered by a regulatory requirement, with type and frequency dictated by that regulation. Involves hands-on examination, reviewing records, compiling reports, gathering supporting detail. The resulting assessment covers current state and may recommend future improvements.

Penetration Tests

-
Physical penetration testing: OS-level security can be bypassed entirely through physical access (modify the boot process, boot from external media, swap OS files), so physical controls (locked doors, badge access, elevators) get tested directly, not just assumed.
-
Pentesting perspectives:
PerspectiveRole
OffensiveRed team, attacks systems and hunts for exploitable vulnerabilities
DefensiveBlue team, detects attacks in real time and blocks unauthorized access
IntegratedOngoing cycle combining both, find and patch exploitable systems, then retest
-
Working knowledge going in defines the test type: known environment (full disclosure, tester has full system info), partially known environment (mix of known/unknown, focused on specific systems/apps), unknown environment (tester starts blind, a "blind" test).
-
Reconnaissance gathers a digital footprint before any attack begins, maps the security posture and network layout, narrows the attack area to key systems.

Security Awareness Training

Security awareness = training and comms aimed at getting users to recognize threats and act securely. People get targeted specifically because human error routinely bypasses technical controls that would otherwise stop an attack.

Standard awareness curriculum: phishing, password hygiene, MFA usage, data handling, safe browsing, removable media risk, physical security, remote work security, incident reporting, clean desk habits, acceptable use.

Social engineering: manipulating people into handing over access, information, money, or taking some action on the attacker's behalf. Red flags to train on:

-
Artificial urgency or pressure
-
Requests to keep something secret
-
Unexpected attachments or suspicious links
-
Sender address that looks slightly off
-
Anyone asking for a password or MFA code directly
-
Gift card or payment requests
-
Impersonation of an executive, vendor, or IT support

Phishing defense habits: verify sender address, treat attachments with suspicion, hover links before clicking, watch for lookalike domains and spelling tricks, never enter credentials via a link that arrived unexpectedly, report anything suspicious rather than ignoring it.

Remote work introduces its own risk set: public Wi-Fi, shared devices, shoulder surfing, lost/stolen laptops, weak home router config, unsanctioned cloud storage use. Counter with VPN when required, screen locking, MFA, keeping devices patched, careful handling of company data, and fast reporting of lost hardware.

Reporting culture matters as much as the training content. Users should know how to flag: suspicious email, a lost device, suspected credential compromise, unusual system behavior, accidental data exposure. Awareness only pays off if reporting is easy and the org actually encourages it rather than punishing people for raising a hand.

Phishing campaigns as an internal testing tool: orgs send their own phishing emails to measure how many employees click, an automated process with centralized reporting on incorrect clicks. Users who click get immediate feedback and follow-up training, sometimes scheduled in person. Recognition cues to train on: spelling/grammar errors, domain or email inconsistencies, unexpected attachments, requests for personal info.

Anomalous behavior recognition, three buckets:

CategoryExamples
RiskyModifying the hosts file, replacing a core OS file, uploading sensitive files
UnexpectedLogon from another country, spike in data transfers
UnintentionalTypo'd domain name, misplaced USB drive, misconfigured security setting

Reporting and monitoring: track metrics like phishing click rate, password manager adoption, MFA use, password sharing, ideally through automation. First occurrence of an issue is a training opportunity; recurring occurrences flag a long-term monitoring problem and need extra help for repeat offenders.

Program development: stand up a security awareness team (roles for training, monitoring, policy creation), set a minimum awareness level (delivery mix of emails/posters/notices/training, depth scaled to job function), fold in compliance mandates (PCI DSS, HIPAA, GDPR), define metrics to know if the program's working and where to focus updates.

Program execution: build the training materials, document how success gets measured, identify the stakeholders who need ongoing metrics, deploy through whatever mix fits (classroom, posters, weekly emails), track training completion via an automated reporting system.

Insider threat: hard to guard against since the access is already legitimate. Countered with multiple-approval requirements on critical processes and heavy monitoring of files/systems, the goal is making an unauthorized change difficult to slip through unnoticed.

Situational awareness for users: stay alert to software attacks (email links, attachments, unusual URLs, suspicious texts) and physical attacks (a USB drive left in a FedEx envelope, an unlocked building door). Policy/handbooks should document the requirements and stay referenceable online.

Operational security: view the org's data the way an attacker would, so users can identify what's actually sensitive and keep it private.

Removable media and cables: unknown USB drives can carry malware, unknown cables can connect to a malicious device on the other end, both worth flagging in training.

Hybrid/remote work environments carry their own risk set beyond the general remote-work bullets above: no access to office-level physical/social safeguards, so additional endpoint security and VPN-specific policy matter more.
